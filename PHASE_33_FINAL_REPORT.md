## 2. Root cause of P3019

Prisma 5.22 allows exactly one migrations directory per schema. That directory's `migration_lock.toml` said `postgresql` while the datasource said `sqlite`, and the directory held a PostgreSQL-only baseline (2× `BYTEA`, `ALTER TABLE … ADD CONSTRAINT`). Proven incompatible with SQLite:

```
$ sqlite3 <empty> < 20261007183000_postgresql_baseline/migration.sql
EXPECTED FAILURE: OperationalError near "CONSTRAINT": syntax error
```

Every migrate command failed before touching a database — so no migration could be created, reviewed or applied.

## 3. Root cause of P2022

Two file tables were never given the Phase 30 / Phase 32 columns: `ContentMedia` (10) and `MessageAttachment` (8) = **18 columns**. Confirmed column by column (the previously reported count is still exactly right). Because Prisma selects every scalar column, `content_media.findFirst()` threw `P2022 … originalName does not exist`, breaking every media and attachment path. `count()` still worked — which is why earlier smoke checks looked healthy.

## 4. Migration strategy selected and why

**Archive PostgreSQL verbatim; establish a fresh, introspected SQLite history.**

- Rejected: flipping `migration_lock.toml` to `sqlite` while keeping PG DDL in the history (pretends two incompatible histories are one).
- Rejected: a second schema file per provider (4,311 duplicated lines, two sources of truth for 213 models).
- Chosen: `prisma/migrations.postgresql/` holds the originals with `MANIFEST.sha256` + README (verified 4/4 unchanged); `prisma/migrations/` holds a SQLite-only history whose baseline was **generated by introspecting a byte-identical copy of the real database**, so it describes reality rather than an aspiration. Nothing was marked applied except via Prisma's documented `migrate resolve --applied` baselining mechanism, and only on copies.
- Full rationale: `PHASE_33_MIGRATION_PROVIDER_DECISION.md`.

**Additional defects found while doing this:**

1. **CRITICAL, silent:** the Phase 30 migration used `ADD COLUMN … NOT NULL DEFAULT CURRENT_TIMESTAMP`, which SQLite **rejects as soon as the table has a row** ("Cannot add a column with non-constant default"). It passed earlier only because `content_media` contained 0 rows. Repaired in the SQLite variant (nullable → backfill from `createdAt` → NOT NULL enforced by a rebuild).
2. **HIGH:** `ALTER TABLE` cannot create the foreign key for `content_media.organizationId`; the migrated DB was missing the tenant constraint and drifted from the schema. Fixed by a SQLite-only table rebuild that also normalises `updatedAt` to Prisma's `DATETIME`.
