# Workflow Engine Architecture — Phase 19

## 1. Scope and trust boundaries

All execution is server-side in the existing Next.js LMS and Prisma database. The browser can author only a strict JSON definition from fixed trigger/condition/step schemas; it cannot submit JavaScript, SQL, expressions, provider credentials or arbitrary network URLs. The user session is revalidated from the database, permissions are resolved from the identity/role service, and every management query/mutation is scoped to the caller's organization.

Current authorized roles are organization-admin/Super-Admin and Training Admin when their corresponding stored permissions are granted. `workflows.view`, `workflows.manage`, `workflows.execute` and `workflows.approve` are default-deny permission keys. No student grant exists. Teacher-specific group-scoped workflow access is not yet implemented.

## 2. Event model and EventBus

`EventBus.publish()` accepts a server-created event only. Required fields:

| Field | Stored representation |
|---|---|
| `event_id` | `WorkflowEvent.id` |
| `event_type` | Registry string, e.g. `LESSON_COMPLETED` |
| `organization_id` | Required tenant key |
| `actor_id` / `subject_user_id` | Optional user identifiers |
| `object_type` / `object_id` | Optional bounded target reference |
| `timestamp` | `occurredAt` UTC instant |
| `source` | Bounded producer identifier |
| `event_version` | Integer, defaults to 1 |
| `metadata` | Small, scalar-only allowlisted JSON |
| `idempotency_key` | Unique within organization |

Sensitive metadata keys (credentials, passwords, tokens, email, phone, address, answer and message) are discarded; values are bounded scalars, not arbitrary nested payloads. Event row status: `QUEUED → PROCESSING → PROCESSED`, or retry to `QUEUED` / terminal `FAILED`. `lockedAt`, attempt count and `nextAttemptAt` support crash recovery and backoff.

The event catalog covers user, enrollment, course/module/lesson, practice/quiz/exam, diagnostic/placement, speaking/listening/writing, assignment, attendance, streak/gamification, certificate, communication/recommendation/review and integration sync types. Current LMS producer: lesson completion. Manual trigger events are generated only by the authorized run route and target a workflow ID in the same organization.

## 3. Workflow and version model

`Workflow` is the organization-scoped lifecycle pointer. Each immutable `WorkflowVersion` stores a strict definition snapshot, checksum, creator and publication time. Saving an edit creates the next draft version; it does not overwrite a published snapshot. The previously published version remains active while the new version awaits validation/publication. `WorkflowRun` stores the exact `versionId` and event row, so historical runs do not follow the current draft.

Lifecycle values: `DRAFT`, `TESTING`, `PUBLISHED`, `PAUSED`, `ARCHIVED`. The current API emits draft/published/paused/archived. `TESTING` is a schema vocabulary value; simulations do not persist a testing lifecycle state.

Run lifecycle values: `QUEUED`, `RUNNING`, `WAITING`, `COMPLETED`, `FAILED`, `CANCELLED`, `SKIPPED`. Each run records the organization, workflow/version, triggering event, subject, current step, retry count, timestamps and error summary. `WorkflowRunStep` stores bounded input/output snapshots and status/attempts for each executed step.

## 4. Trigger matching

Supported now:

- `EVENT` — exact match on one allowlisted event type.
- `MANUAL` — generated by an authorized admin action; matched only when the event's organization, object type and workflow ID agree.

Not supported yet: recurrence/calendar schedules, dates, relative schedule triggers, webhook/import triggers, shift/class calendar triggers and user-defined cron. Those must not be published as if active. The builder warns when an event type has no connected producer.

## 5. Condition evaluator

Definition shape: a top-level `AND` or `OR` group containing at most 20 rules. No code execution or user-defined paths. Allowlisted paths:

- `user.role`, `user.englishLevel`, `user.groupId`
- `event.eventType`, `event.objectType`, `event.source`

Operators: `EQ`, `NE`, `IN`, `NOT_IN`, `CONTAINS`, `IS_EMPTY`, `IS_NOT_EMPTY`. Missing subjects are evaluated against a system context; a provided subject that cannot be resolved inside the event organization causes a skip, not a cross-tenant lookup. Other condition families (scores, attendance thresholds, streak, XP, dates and prior results) remain future work.

## 6. Action engine

The action allowlist is a Zod discriminated union:

1. `SEND_NOTIFICATION` — internal recipient is the event subject; user must still be active in the same organization. It delegates to the Phase 12 Communication Hub, which handles preferences, quiet hours, throttling and existing provider configuration. Only `{{firstName}}` and `{{eventType}}` substitution is performed. Links must be local paths.
2. `CREATE_LEARNING_RECOMMENDATION` — requires an active in-organization student; creates the existing adaptive recommendation model with a run/step marker for idempotent retry.
3. `WAIT` — bounded 1 minute–30 day delay; advances the cursor and persists `nextRunAt`.
4. `REQUIRE_APPROVAL` — creates a pending approval with expiry and pauses the run. An authorized approval queues continuation; rejection cancels the run; expiry cancels on the next worker tick.

No arbitrary action plug-ins or provider calls are available. XP awards, mascot reactions, certificates, grade writes, enrollment/course assignments, attendance writes, webhooks, email/SMS/push-only actions and exports need separately audited service adapters before they can be offered.

## 7. Server-side service boundaries

The workflow service module exposes named boundaries for `WorkflowEngine`, `EventBus`, `EventDispatcher`, `RuleEngine`, `ConditionEvaluator`, `ActionExecutor`, `WorkflowQueue`, `WorkflowScheduler`, `WorkflowRunTracker`, `WorkflowApprovalService`, `WorkflowValidationService`, `WorkflowSimulationService`, `WorkflowAuditService`, `WorkflowRateLimitService`, `WorkflowRetryService` and `WorkflowLoopProtectionService`. The engine/dispatcher invokes the rule, condition, action, retry and loop-protection logic; API routes use the audit/approval/rate-limit/simulation boundaries. These remain server-side modules, not browser-executable plug-ins.

## 8. Queue/worker architecture

```text
LMS mutation
   └─ EventBus.publish() ──> workflow_events (durable QUEUED row)
                                  │
Trusted scheduler ──POST + Bearer secret──> /api/internal/workflow-worker
                                  │
                         organization-scoped dispatcher
                                  │
          published workflow/version match + unique run(event,version)
                                  │
                  condition evaluator → bounded steps
                                  │
          notification/recommendation | WAIT | APPROVAL
                                  │
             run steps + outcome + audit/notification systems
```

The ordinary lesson-completion request persists the event and does not execute the workflow. A worker poll processes bounded batches (up to 5 items per organization per tick, 10 organizations per call). It claims events/runs with conditional updates; each tick examines up to five due events and up to five due runs per organization, while the endpoint processes at most ten organizations. Stale processing locks are reclaimed after five minutes. This is a database queue, not Redis/Temporal/BullMQ. No scheduler is included; deployment must configure one and keep `WORKFLOW_WORKER_SECRET` server-only (32+ characters). The worker endpoint returns aggregates, not organization identifiers.

## 8. Retry and idempotency

- Event idempotency: unique `(organizationId, idempotencyKey)`.
- Run idempotency: unique `(workflowId, versionId, eventId)`.
- Step idempotency: unique `(organizationId, runId:stepIndex)`.
- Recommendation action: persistent marker in existing recommendation evidence.
- Notification action: stable title/type/link and existing Communication Hub duplicate suppression.
- Event dispatch and action failures retry with capped exponential delay and a maximum of five attempts; errors are bounded and stored without secrets.
- No action republishes a workflow event. EventBus rejects sources with a `WORKFLOW_`/`WORKFLOW:` prefix and current actions do not call EventBus, stopping recursive chains by construction.

The database cannot make external provider acceptance plus local idempotency update one distributed transaction. Provider delivery receipts/reconciliation are required before promising exactly-once email/webhook behavior.

## 9. Approval behavior

Approval records bind to a run/step and inherit the run's organization. Only callers with `workflows.approve` in that organization may decide. Updates use a conditional pending-state claim, record actor/time/reason, update the matching step and queue continuation or cancel. Approval does not itself call a certificate service or alter official records. Expired approvals are marked/cancelled by the protected worker.

## 10. Simulation, auditing and safety

`POST /api/admin/automation/simulate` validates the same definition, loads an optional subject only within the caller organization and returns trigger/condition/action preview metadata with `sideEffectsApplied:false`. It creates an audit record but does not enqueue or execute actions. Workflow management and approval mutations are audited with non-sensitive identifiers/status only.

Rate/resource guards: max 200 non-archived workflows per organization, max 20 steps/rules per definition, 10,000 pending/processing events per organization, manual-run cap 20 per actor per hour, worker batch limits and existing Communication Hub notification caps. No SSRF-capable action exists; external links are rejected rather than fetched.

## 11. Database entities

- `workflow_events` — durable event/outbox and event idempotency.
- `workflows`, `workflow_versions` — org lifecycle and immutable snapshots.
- `workflow_runs`, `workflow_run_steps` — execution and step history.
- `workflow_approvals` — human decisions and expiry.
- `workflow_idempotency_records` — action retry barriers.

The current repo uses Prisma schema sync without an existing migration history. Local tables were added with a non-destructive `db push`; production rollout needs a reviewed migration plan and backup.
