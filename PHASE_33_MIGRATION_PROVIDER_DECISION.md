# PHASE 33 — Migration Provider Decision Record

**Date:** 2026-10-25
**Decision:** SQLite is the development/application database of this repository. The PostgreSQL migration history is preserved but **quarantined**, and a fresh, introspected SQLite history is established at the standard Prisma location.

---

## 1. The four databases, stated separately

| # | Role | Actual state | Evidence |
|---|---|---|---|
| 1 | **Current development application** | SQLite, `file:./dev.db` → `prisma/dev.db` (4,517,888 bytes, 213 tables, 87 users) | `schema.prisma` `provider = "sqlite"`; `.env` `DATABASE_URL` (value not printed) |
| 2 | **Automated tests** | SQLite, throwaway copies only (`e2e/e2e.db`, `e2e/mig33/*.db`); storage is the local adapter rooted at `e2e/storage` | `e2e/seed.ts`, `scripts/test-idor-live.mjs` |
| 3 | **Intended staging** | **PostgreSQL** — evidenced only by `prisma/migrations/20261007183000_postgresql_baseline` and Phase 28/31 notes. **Not configured, not reachable, NOT VERIFIED.** | no PG host, no PG `DATABASE_URL` |
| 4 | **Intended production** | **NOT FORMALLY SPECIFIED** anywhere in the repository. This phase does **not** declare one. | searched `.env.example`, docs, config |

SQLite is therefore **not** declared to be the production target. It is the provider of the running application, and PostgreSQL remains the documented-but-unbuilt staging intent.

## 2. Root cause of P3019

```
$ npx prisma migrate status          # (before this phase)
Error: P3019
The datasource provider `sqlite` specified in your schema does not match the one
specified in the migration_lock.toml, `postgresql`.
```

Three facts combine into a dead end:

1. Prisma 5.22 supports **exactly one** migrations directory per schema — always `<schemaDir>/migrations`.
2. `prisma/migrations/migration_lock.toml` said `provider = "postgresql"` while `prisma/schema.prisma` says `sqlite`.
3. The directory contained a **PostgreSQL-only** baseline. Proven, not assumed:

```
$ sqlite3 <empty> < 20261007183000_postgresql_baseline/migration.sql
EXPECTED FAILURE: OperationalError near "CONSTRAINT": syntax error
```
It uses `BYTEA` (2 occurrences) and `ALTER TABLE … ADD CONSTRAINT`, neither valid in SQLite.

Consequence: **every** migrate command (`dev`, `deploy`, `status`, `resolve`) failed before touching any database. No migration could be created, reviewed or applied.

## 3. Options considered

| Option | Rejected because |
|---|---|
| **A.** Flip `migration_lock.toml` to `sqlite` and keep the directory as-is | Leaves a PostgreSQL-only baseline inside a SQLite history. The first `migrate deploy` would try to execute PG DDL. Silently pretends two incompatible histories are one — exactly what the phase forbids. |
| **B.** Second schema (`prisma/sqlite/schema.prisma`) with its own migrations dir | Prisma requires a complete model set per schema → 4,311 duplicated lines that will drift from the real one. Two sources of truth for 213 models is a worse defect than the one being fixed. |
| **C. (chosen)** Archive the PostgreSQL history verbatim, establish a fresh, introspected SQLite history | One schema, standard directory, PG preserved and provably unchanged, no false "applied" records. |

## 4. What was actually done

```
prisma/
├── schema.prisma                     unchanged (provider = "sqlite", 213 models)
├── migrations/                       ← SQLite history (Prisma's standard location)
│   ├── migration_lock.toml           provider = "sqlite"
│   ├── 20261001000000_sqlite_baseline/            introspected from the real DB
│   ├── 20261010000000_phase30_storage_metadata/   original SQL + 2 documented repairs
│   ├── 20261010000001_phase32_tenant_isolation/   byte-identical to the original
│   └── 20261010000002_phase33_sqlite_file_integrity/  SQLite-only table rebuild
└── migrations.postgresql/            ← preserved, never read by Prisma
    ├── MANIFEST.sha256               sha256 of all 4 original files
    ├── README.md                     purpose, provenance, restore instructions
    └── 20261007183000_postgresql_baseline/, 202610…_phase30…, 202610…_phase32…
```

- **Nothing was deleted.** The three original directories and `migration_lock.toml` were copied to `prisma/migrations.postgresql/`, hashed into `MANIFEST.sha256`, verified file-by-file, and only then removed from `prisma/migrations`. `sha256sum -c MANIFEST.sha256` passes (4/4 OK).
- **Nothing was falsely marked applied.** The baseline was generated by *introspecting a byte-identical copy of the real database* (`prisma migrate diff --from-empty --to-url …`), i.e. it describes the database as it actually is — including the absence of the 18 columns. It is registered with `migrate resolve --applied`, which is Prisma's documented baselining mechanism, and only on a disposable copy.
- **The baseline is ordered first** (`20261001000000` < `20261010000000`) so the pending migrations apply after it.

## 5. Why the SQLite copies are not byte-identical to the originals

`20261010000000_phase30_storage_metadata` needed **two** provider-specific repairs, generated by `scripts/db/build-sqlite-migrations.mjs`, which asserts the delta:

```sql
-- original (PostgreSQL and SQLite-with-empty-table only)
ALTER TABLE "content_media" ADD COLUMN "updatedAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP;

-- SQLite repair
ALTER TABLE "content_media" ADD COLUMN "updatedAt" DATETIME;
UPDATE "content_media" SET "updatedAt" = COALESCE("createdAt", CURRENT_TIMESTAMP) WHERE "updatedAt" IS NULL;
```

**Why this was necessary — measured, not theorised:**

| content_media rows | `ADD COLUMN … NOT NULL DEFAULT CURRENT_TIMESTAMP` |
|---|---|
| 0 | accepted |
| 1 | **REJECTED — "Cannot add a column with non-constant default"** |

The Phase 30 migration therefore would have **failed the moment any file existed** — the development database happened to have zero media rows, which masked a production-breaking defect.

`20261010000001_phase32_tenant_isolation` required no repair (byte-identical).

`20261010000002_phase33_sqlite_file_integrity` is new and SQLite-only: SQLite cannot `ALTER TABLE ADD CONSTRAINT`, so the foreign key on `content_media.organizationId` and Prisma's canonical `DATETIME` shape require the standard rebuild (create → copy every row → drop → rename). The header of the file states this.

## 6. Consequences and how to reverse the decision

- `npx prisma migrate dev / deploy / status` now work against SQLite. Verified: `migrate status` → "Database schema is up to date!"; `migrate dev` → "Already in sync, no schema change or pending migration was found." (no reset prompt).
- A guarded runner (`scripts/db/guarded-migrate.mjs`) refuses to run against `prisma/dev.db`, any non-SQLite URL, or any path that looks like production/shared infrastructure.
- **To return to a PostgreSQL deployment:** provision the instance, point a PostgreSQL schema at it, and restore the directory with
  `node scripts/db/restore-postgresql-migrations.mjs` (copies `prisma/migrations.postgresql/` back to `prisma/migrations/`, verified against the manifest). The PostgreSQL DDL has **not** been validated on a live server and remains **NOT VERIFIED**.
- **The SQLite and PostgreSQL histories must never be mixed in one directory.** The archive boundary is what keeps that impossible.
